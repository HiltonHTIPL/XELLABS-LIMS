| New Sample registration blocked for IST (and any UTC+ timezone) users — naive datetime-local sent without offset (2026-07-13) | Single Source of Truth (correct at the one place data crosses the client/server boundary) | New Sample registration failed with "Sample MNLS-xxxx was created in the lab system, but the local mirror failed" for every submission from a browser in a timezone ahead of UTC. Root cause: `NewSampleShell.tsx` sent the raw `<input type="datetime-local">` value (a naive wall-clock string with no timezone offset, e.g. "2026-07-13T14:54") straight through as `collection_date`. Django has `TIME_ZONE="UTC"` + `USE_TZ=True`, so it read that naive string as 14:54 **UTC** — for a user actually in IST (UTC+5:30), true current UTC time is ~09:2x, so the value looked like a timestamp ~5.5 hours in the future and tripped the serializer's "Sample date cannot be in the future" guard. The frontend's own pre-submit future-date check never caught this because it compares two naive `Date` objects constructed the same way on the same machine, so the mismatch only appears once the value crosses to the server. Fixed by converting via `new Date(f.dateSampled).toISOString()` before sending — `new Date()` parses a naive datetime-local string using the *browser's* local timezone, so `.toISOString()` produces the correct UTC instant. Verified by simulating the browser's actual IST timezone (`TZ=Asia/Kolkata`) in Node and confirming "14:54" now correctly converts to "09:24Z", then replaying the exact Django mirror-creation call with that corrected value — 201, no future-date rejection. Also recovered the orphaned SENAITE sample from the original failed attempt (created a matching Django mirror row for it, since it had no local record at all). Note: the same naive-datetime pattern likely exists on other date fields elsewhere in the app (Sample edit form, Instrument Maintenance, Tasks) — not fixed here, flagged for a follow-up sweep.
