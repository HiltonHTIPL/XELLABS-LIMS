XelLabs LIMS — What to configure after pushing to main

📅 2026-07-03 🔖 Branch: HIlton-update → main 👤 Prepared by: Hilton (Hephzibah Technologies)
Read this before running docker compose up. Several environment variables that previously had insecure defaults are now required — the app will refuse to start without them on any non-local machine. This document tells you exactly what to create and where.
01

What was changed in this branch

This branch contained security hardening, bug fixes, and deployment readiness work. The table below lists every change with a severity rating.

# Severity What changed Why it matters
1 🔴 Critical DEBUG no longer defaults to True Django debug mode exposes full stack traces, env vars, and SQL queries to any browser
2 🔴 Critical SECRET_KEY has no fallback — app crashes if unset A known public placeholder key lets anyone forge session cookies
3 🔴 Critical SESSION_SECRET has no fallback — frontend crashes if unset A weak session secret lets anyone forge JWT tokens
4 🔴 Critical Client creation error 500 fixed Creating a new client in the UI returned HTTP 500. Now wrapped in correct schema context.
5 🔴 Critical Duplicate client IDs now rejected (migration applied) Previously the API would accept two clients with the same Client ID, corrupting data
6 🔴 High Django port 8001 now bound to 127.0.0.1 only Previously exposed directly on all interfaces — reachable from the internet
7 🔴 High SENAITE port 8080 now bound to 127.0.0.1 only Same as above — SENAITE admin was internet-accessible
8 🟠 High Hardcoded QA IP 34.30.6.247 removed from next.config.ts Now driven by NEXT_PUBLIC_ALLOWED_ORIGINS env var — add your server's IP there instead
9 🟠 High Material Icons CSP fix Google Fonts CDN was blocked by the Content Security Policy — all icons showed as raw text
10 🟠 High Unknown tenant schema now returns 404 (not silently routing to wrong data) Requests with an invalid X-Tenant-Schema header were previously falling back to the public schema
11 🟡 Medium Session cookie changed to sameSite: strict HIPAA compliance — prevents cross-site session sharing
12 🟡 Medium DRF rate limiting added (20 req/min anon, 120 req/min logged in) Prevents brute-force login attempts

03

Create: root .env file

Create this file at the project root on the QA server. It does not exist in the repo (gitignored). Never commit it.

Required: SESSION_SECRET and DJANGO_SERVICE_TOKEN have no defaults in the new code. The frontend container will crash at startup if either is missing or shorter than 32 characters.
📄 /home/ubuntu/XELLABS-LIMS/.env Create this file 
# XelLabs LIMS — QA Environment
# Place at project root. NEVER commit to git.

# ── Django ──────────────────────────────
DEBUG=False
SECRET_KEY=REPLACE_WITH_50_CHAR_SECRET_KEY
ALLOWED_HOSTS=localhost,127.0.0.1,django,YOUR_QA_IP_OR_DOMAIN
CORS_ALLOWED_ORIGINS=http://YOUR_QA_IP:3000

# ── Database ─────────────────────────────
DB_NAME=xellabs_lims
DB_USER=xellabs_user
DB_PASSWORD=REPLACE_WITH_STRONG_DB_PASSWORD

# ── Redis ─────────────────────────────────
REDIS_PASSWORD=REPLACE_WITH_STRONG_REDIS_PASSWORD

# ── SENAITE ───────────────────────────────
SENAITE_ADMIN_PASSWORD=REPLACE_WITH_NEW_SENAITE_PASSWORD

# ── Frontend / Next.js ────────────────────
SESSION_SECRET=REPLACE_WITH_64_CHAR_HEX_STRING
DJANGO_SERVICE_TOKEN=REPLACE_WITH_40_CHAR_HEX_TOKEN
NEXT_PUBLIC_ALLOWED_ORIGINS=YOUR_QA_IP:3000

# ── Node ──────────────────────────────────
NODE_ENV=production

How to generate each secret

Run these commands on the QA server (Python 3 required):

# SECRET_KEY (50 chars)
python3 -c "import secrets; print(secrets.token_urlsafe(50))"

# SESSION_SECRET (must be 64 hex chars = 32 bytes)
python3 -c "import secrets; print(secrets.token_hex(32))"

# DJANGO_SERVICE_TOKEN
python3 -c "import secrets; print(secrets.token_hex(20))"

# DB_PASSWORD and REDIS_PASSWORD
python3 -c "import secrets; print(secrets.token_urlsafe(24))"
04

Create: backend .env file

A second .env file is needed inside the backend directory. Django reads this directly via the env_file directive in docker-compose.yml.

📄 /home/ubuntu/XELLABS-LIMS/xellabs-backend/.env Create this file 
# Django backend environment — QA server
DEBUG=False
SECRET_KEY=<same value as root .env SECRET_KEY>
DB_NAME=xellabs_lims
DB_USER=xellabs_user
DB_PASSWORD=<same value as root .env DB_PASSWORD>
DB_HOST=postgres
DB_PORT=5432
REDIS_PASSWORD=<same value as root .env REDIS_PASSWORD>
SENAITE_ADMIN_PASSWORD=<same value as root .env SENAITE_ADMIN_PASSWORD>
ALLOWED_HOSTS=localhost,127.0.0.1,django,YOUR_QA_IP_OR_DOMAIN
CORS_ALLOWED_ORIGINS=http://YOUR_QA_IP:3000
Note: DB_HOST must stay as postgres (the Docker service name), not localhost. Django runs inside a container and talks to the database over the Docker network — not over the host loopback.
05

No manual file edits needed for next.config.ts

The hardcoded QA IP 34.30.6.247 has been removed from next.config.ts. The allowed origins are now read from the NEXT_PUBLIC_ALLOWED_ORIGINS env var you set in the root .env file above.

You only need to set the env var — no file editing required:

# In root .env:
NEXT_PUBLIC_ALLOWED_ORIGINS=YOUR_QA_IP:3000,your-qa-domain.com:3000

Multiple origins are comma-separated. Add as many as needed for QA, staging, and production.

What happens without this: Server action buttons (Create Client, Register Sample, etc.) will silently do nothing. No error shown — Next.js rejects the action before it runs. This is the most common "why is nothing working?" symptom on a new server.
06

Deploy steps — run in this order

1

Pull the latest code from main

cd /home/ubuntu/XELLABS-LIMS
git pull origin main
2

Create both .env files

Use the templates from Sections 03 and 04 above. Fill in all REPLACE_WITH_ placeholders with generated values.

3

Build and start all containers

docker compose up -d --build

Use --build every time — this branch changes requirements.txt, package.json, and Dockerfile logic. Running without --build will use a stale image.

4

Wait for all services to become healthy

# Check status (wait until all show "healthy")
docker ps --format "table {{.Names}}\t{{.Status}}"

# If django is unhealthy, check logs:
docker logs xellabs-lims-django-1 --tail 30

# If frontend is unhealthy:
docker logs xellabs-lims-frontend-1 --tail 30
5

Run database migrations

Migrations run automatically on startup via the Django container's entrypoint command. Verify they completed with no errors:

docker logs xellabs-lims-django-1 2>&1 | grep -E "migrate|ERROR|Running"

You should see lines like Running migrations: 0007_add_unique_client_id with no ERROR lines.

6

Change default passwords

See Section 08 below. Change the SENAITE admin password and set the Django admin password before sharing the QA URL with anyone.

7

Run the verification checklist

See Section 07 below. Do not mark QA as ready until all items are checked.

07

Verification checklist — run after every deploy

Container health

  • docker ps — all 6 containers show healthy: postgres, redis, django, celery, celery-beat, frontend
  • No ERROR or RuntimeError lines in docker logs xellabs-lims-django-1 --tail 30
  • No Error lines in docker logs xellabs-lims-frontend-1 --tail 20

API smoke test (from the QA server itself)

  • curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8001/api/auth/login/ -X POST -d '{"username":"admin","password":"admin"}' -H 'Content-Type: application/json' → should return 200
  • curl -s http://127.0.0.1:8001/api/clients/ -H "Authorization: Token YOUR_TOKEN" -H "X-Tenant-Schema: hl-01" → should return JSON with a results array

Frontend UI — open in browser

  • Navigate to http://YOUR_QA_IP:3000 → login page loads, no broken icons (all icons should be filled symbols, not text like "person")
  • Log in as admin → dashboard loads without JavaScript errors in browser console
  • Go to Clients → click New Client → fill in name + client ID → submit → client appears in list (no Error 500)
  • Go to Sample Types → click New Sample Type → fill in name + prefix → submit → appears in list
  • Go to Sample Register → click Register Sample → select client + sample type → submit → sample appears in list with status registered

Security check

  • Try accessing http://YOUR_QA_IP:8001 from your laptop (outside the server) → should be unreachable (connection refused)
  • Try accessing http://YOUR_QA_IP:8080 from your laptop → should be unreachable
  • Confirm .env files are NOT tracked: run git status on the server → neither .env file should appear
08

Changing default passwords

Django admin password

docker exec -it xellabs-lims-django-1 python manage.py changepassword admin

SENAITE admin password

1. Log in at http://127.0.0.1:8080/senaite using admin / admin

2. Go to Site Setup → Users → admin → Change Password

3. After changing, update SENAITE_ADMIN_PASSWORD in both .env files to match

4. Rebuild so the updated env var is picked up:

docker compose up -d --build django celery celery-beat

Client user passwords (when a new client is created)

When you create a new client via the UI, the system auto-generates a random password for their account. That password is not displayed or emailed (email delivery is not built yet). To set it manually:

# Replace CLIENT_ID with the actual client username (e.g. E2E-001)
docker exec -it xellabs-lims-django-1 python manage.py changepassword CLIENT_ID

Then share the username and new password with the client directly.

09

Emergency rollback

Never run docker compose down -v — the -v flag deletes the postgres_data volume and all lab data is permanently lost.

Roll back to the previous commit

# Find the last working commit hash
git log --oneline -5

# Check out that commit
git checkout <commit-hash>

# Rebuild (without -v — data is safe)
docker compose down
docker compose up -d --build

If a container won't start after a failed deploy

# Force-recreate only the broken container
docker compose stop django
docker compose up -d --force-recreate django

# Check what went wrong
docker logs xellabs-lims-django-1 --tail 50

If migrations fail

# Run migrations manually
docker exec -it xellabs-lims-django-1 python manage.py migrate_schemas --shared --noinput
docker exec -it xellabs-lims-django-1 python manage.py migrate_schemas --noinput
